# Engineering log

Hard problems as they come up, what was tried, and what worked. This becomes the write-up and the interview stories.

## 2026-10-25: MinIO images disappeared

Phase 0's compose file pointed at `minio/minio`. Every tag now returns "access denied": MinIO stopped publishing community images. Switched to SeaweedFS's S3 gateway (ADR-0012). Because services only use the S3 API through boto3, the swap touched the compose file and one config file, nothing in application code. Lesson: depend on the protocol, not the product.

## 2026-10-25: ClickHouse "unhealthy" while serving fine

The ClickHouse container never passed its healthcheck, so the ingest service never started. The server was up: `wget http://127.0.0.1:8123/ping` returned `Ok.` But the container has no IPv6, so ClickHouse logged `Listen [::]:8123 failed` and bound IPv4 only, while Alpine's `/etc/hosts` resolves `localhost` to `::1` first. The healthcheck's `wget localhost` was refused. Fix: healthchecks use `127.0.0.1`. Lesson: "unhealthy" means the check failed, not the service; test the check itself first.

## 2026-10-25: Worker died for good when Redis restarted

Found by driving the stack, not by the tests: stopping and starting Redis left the worker container `Exited (1)`. `xreadgroup` raised `ConnectionError: Connection closed by server`, nothing caught it, and the service had no restart policy. Unit tests never restart Redis, so they couldn't see it. Fix: `run_forever` catches connection errors, backs off exponentially (1s, 2s, 4s, capped at 30s), and re-ensures the consumer group after reconnecting (Redis may come back without it). Ingest and worker also get `restart: unless-stopped` for crashes we haven't thought of. Lesson: a background consumer's main loop must treat its broker going away as normal weather.

## 2026-10-25: The trace summary view wouldn't create

ClickHouse refused `traces_mv` at startup (`ILLEGAL_AGGREGATION: min(start_time) AS start_time is found inside another aggregate function`). The view's output aliases have to match the `traces` columns, so `min(start_time) AS start_time` was required, but ClickHouse resolves a name to an alias before a column: every later `start_time` in the same SELECT, such as `max(coalesce(end_time, start_time))`, meant the aggregate. Fix: read from a subquery that renames the source columns (`start_time AS s_start`) and aggregate those. The web app's summary query uses aliases that differ from the column names for the same reason. Lesson: in ClickHouse, an alias that matches a column name shadows it everywhere in that SELECT.

## 2026-10-25: A dead OR branch still runs

The trace list's first page failed with `Cannot read DateTime`. The cursor filter was `{before} = '' OR t_start < parseDateTime64BestEffort({before})`, and ClickHouse folds constants before it short-circuits, so it parsed `''` anyway. Fix: no special case in SQL; the first page passes a far-future cursor. Lesson: don't rely on short-circuit evaluation to guard a parse of a query parameter.

## 2026-10-25: A store outage must not spend an entry's retries

The plan was at-least-once delivery with a dead-letter after 5 deliveries (ADR-0015). Done naively, a ClickHouse outage dead-letters everything: each failed batch stays pending, gets reclaimed after 60 s idle, and its delivery count climbs to 5 in a few minutes. The worker now tells store outages (connection errors) apart from batches a store rejects. On an outage it holds the batches it has and retries them with backoff, without reading or reclaiming, so the delivery count doesn't move. Only real rejections are left pending, to be reclaimed and eventually dead-lettered. Verified by stopping ClickHouse mid-ingest: the pending entry stayed at 1 delivery, and all spans landed after the restart.

## 2026-10-25: A 413 that looked like a network error

A pre-PR review found that a burst of large LLM spans never reached ingest. The exporter batched by count (100 spans), ingest refuses bodies over 5 MB, and 100 spans with 60 KB conversations is 6 MB. Worse, the SDK never saw the 413: ingest rejects on `Content-Length` and closes the connection while the client is still sending, so urllib raised `BrokenPipeError`, which looked like a network blip and got retried three times before the whole batch was dropped. Fix: batches are bounded by bytes (4 MB) as well as count, and a single span too big for any request is sent with its large input or output cut to a prefix and marked `agenttrace.truncated`. The same review found that the exit-time flush retried with backoff, so a down server held a 500-span process open for 18 s; shutdown now gets one attempt per batch, a 2 s deadline, and wakes any in-flight retry. Lesson: a server that rejects early can make an HTTP error look like a transport error, so cap the request on the client.

## 2026-10-26: A trace pinned "forever" would have expired in 2069

The plan for pinning (ADR-0021) was to set `retention_days` to 65535, the UInt16 maximum, about 179 years. The integration test checked the expiry ClickHouse computes for a pinned row, `toDateTime(start_time) + toIntervalDay(retention_days)`, expecting something past 2200, and got 2070-02-21. `DateTime` is seconds since 1970 in a UInt32, so it ends on 2106-02-07, and adding past that wraps around silently: `toDateTime('2106-02-07 06:28:15') + toIntervalDay(1)` is `1970-01-01 23:59:59`. Every pinned trace would have quietly expired in 2069. Fix: pin by setting each row's `retention_days` to the days from its own start to 2106-01-01, so the sum lands just inside the range. The test now asserts the year is 2106. Lesson: "the type's maximum" means forever only if every expression it feeds into holds it too.

An earlier version of the same test inserted traces that were already past a 1-day retention and expected only the pinned one to survive. It failed about half the time, because a regular background merge applies TTL too (`SYSTEM STOP TTL MERGES` doesn't stop it) and could drop the row before the mutation ran. Pinning an expired trace isn't a real case, since "Add to dataset" needs the trace to exist, so the test now checks the computed expiry of fresh traces instead.

## 2026-10-26: The same 413, one layer up

A pre-PR review of Phase 3 found that the eval runner uploaded samples in batches of 20, each sample's output capped at 1 MB and its tool-call arguments not capped at all, against ingest's 5 MB request limit. Twenty 300 KB answers made a 6 MB request; ingest closed the connection mid-upload, the client saw `Broken pipe`, retried three times, and marked the whole experiment `failed` with "couldn't reach" the server. It's the span exporter's 413 from Phase 1 again, in new code that batched by count. Fix: batches are bounded by bytes (4 MB) as well as count, and every sample is shrunk to fit one request on its own: output to 1 MB, each tool-call argument to 4 KB, and all arguments to 1 MB per sample, with NUL replaced, since one NUL also got the whole run refused. The same review found that a run that stopped waited for agent calls still running, with their timeouts no longer enforced, so a hung agent hung the CLI and left the experiment `running`; a stopped run now marks the experiment failed at once and exits without joining agent threads. Lesson: any client of a size-limited endpoint batches by bytes; make that a property of the client, not something each caller remembers.

## 2026-10-26: The merge-base of a merge commit is the base branch's tip

The plan for baselines (ADR-0026) had the CLI run `git merge-base HEAD origin/main`. In a `pull_request` workflow, `actions/checkout` checks out GitHub's temporary merge commit, whose parents are the PR head and the base branch's current tip, so that merge-base is always the tip of `main`: every PR would have compared against whatever `main` ran last, not where it branched, which is the mix-up ADR-0007 exists to avoid. The same commit is also what `GITHUB_SHA` names, so Phase 3 had been recording a commit no baseline could ever match. Fix: on a pull request the runner reads the head SHA from the event payload, records that as the experiment's commit, and computes the merge-base from it, not from `HEAD`. Lesson: in CI, "the commit being tested" and "the commit checked out" can be different commits; name which one you mean.

## 2026-10-26: Forced tool use is gone from the current models

ADR-0027 planned the LLM judge's verdict as a forced tool call (`tool_choice: {"type": "tool"}`), the usual way to get structured output. Checking the API reference before writing it: Opus 5.5, Sonnet 5.5, and Fable 5.1 all answer a forced `tool_choice` with a 400. A judge built that way would have worked on Haiku in tests and failed on the first user who picked a stronger judge model. The judge asks for a JSON schema through `output_config.format` instead, which every current model supports and which guarantees the reply parses. Lesson: check API shapes against current docs, not memory, especially for a parameter the user picks (the judge's model).

## 2026-10-26: ClickHouse had no migrations

Phase 5 adds a `replay_of` column to `traces` and has `traces_mv` fill it. The plan said "a replays migration", but only Postgres had a migration runner: the ClickHouse schema was init SQL, which runs once, on an empty volume. Every existing stack would have kept the old view, and the trace list's "hide replays" filter would have failed on a missing column. Fix: a second migration series, `migrations/clickhouse/`, recorded in a ClickHouse `schema_migrations` table under a Postgres advisory lock. ClickHouse has no transactions, so each statement must be safe to rerun. The view change was the risky part: dropping and recreating `traces_mv` leaves a window where spans the worker inserts are summarized by neither view. ClickHouse 25.8 swaps a materialized view's query atomically with `ALTER TABLE traces_mv MODIFY QUERY`, with no experimental setting; a throwaway container confirmed it before the migration was written. Lesson: "add a column" is a migration only if the store has a way to migrate; check before the plan assumes one.

## 2026-10-26: Naive in the container, aware on the laptop

Phase 6 moves trace reads from the web app into ingest. The new `/v1/traces` passed every unit and integration test, then answered 500 for every trace on the verify stack: "can't subtract offset-naive and offset-aware datetimes". clickhouse_connect returns a `DateTime64(6, 'UTC')` column as a naive datetime when the process's local zone is UTC, and as an aware one otherwise. The integration tests ran on a Mac in another zone and got aware values; ingest runs in a UTC container and got naive ones, and status is computed by subtracting one from `now()`. CI's runners are UTC too, so it would have failed there first. Fix: the trace store makes every datetime aware UTC as it reads it, with a unit test that feeds it naive values, and the integration tests are run with `TZ=UTC`. Lesson: when a library's output depends on the machine's zone, normalize at the boundary, and test the way production runs, not the way the laptop does.

## 2026-10-26: A replay could point at another project's trace

Phase 6's proof includes an integration test that gives project A a trace, a dataset, an experiment, and a replay, then calls every project route at A's ids with project B's key and session. Every read and write came back 403, 404, or 409 except one: `POST /v1/replays` with `replay_of` naming A's trace was 201, and B's replay list for that trace then showed it. Nothing of A's was read, since B supplied the ID, but B could file replays under traces it doesn't own. Every other create checks what it references through a query scoped to the project (a dataset version, an item revision); a replay without an item referenced only a trace ID, which nothing checked. Fix: creating a replay checks that the original trace is in the caller's project, with one query on the `traces` table, and answers 404 when it isn't. A first version read the root input for this, which also fetched the payload from S3 and refused replays of a replay run whose original had expired, a case the replay page handles; the check now also accepts an original the project has replayed before, since its replay runs can outlive it. The unit-test fakes ignore projects, which is why only the test against the real stores caught it. Lesson: a route can reference another project's data through a field in its body as well as through its path, and only a test that tries every route with another project's IDs finds both.

## 2026-10-27: The Anthropic SDK traces itself

Phase 7's bridge sets an OpenTelemetry tracer provider when `agenttrace eval` runs an agent that hasn't set one, so OTel-instrumented agents record. The `anthropic` package depends on `opentelemetry-api` and, once any provider exists, records a GenAI `chat` span for every `messages.create` by default. The demo agent also calls `instrument_anthropic()`, which records the same call as an SDK LLM span, so under the bridge each model call would have arrived twice, nested, with its cost counted twice. A local run against a fake server showed both spans; the eval run on the verify stack, after the fix, had only `instrument_anthropic()`'s. Fix: the bridge drops an OTel `llm` span whose parent is an SDK `llm` span that hasn't ended. The same dependency ruled out the first plan for context: sharing OpenTelemetry's context whenever it's importable would have made our spans children of OTel spans nobody exports, in every app that uses `anthropic`, leaving their traces without a root. Context is shared only once the bridge is installed. Lesson: a library being importable says nothing about whether it's in use, and a dependency can start emitting telemetry the moment someone else configures it.

## 2026-10-27: Pydantic AI's agent span has no input

The translator was written against the GenAI conventions, then checked against what Pydantic AI 2.61 actually sends. Kinds, tokens, tool names and arguments all mapped as planned, but `invoke_agent` carries the run's output and instructions and not its input, and the conventions don't define one. "Add to dataset" and `agenttrace replay` copy the root span's input, so an OTel-only trace couldn't become a test case or be replayed. Fix: the translator reads `input.value` and `output.value`, OpenInference's generic payload attributes, on any span its convention gives no content, and the demo CLI puts the question on its root span that way (ADR-0035). Lesson: check a mapping against a real emitter before building on it; a spec describes what a span may carry, not what any library sends.
